Reference Architectures & Enterprise Design Patterns

Canonical cloud blueprints: Three-tier web applications, event-driven reactive microservices, multi-region active-active vs active-passive, and enterprise landing zone hubs.

1 Real-World Explanation

The Situation: The Value of Proven Blueprints

Architectural patterns are reusable solutions to commonly occurring problems. Rather than designing every cloud system from a blank sheet of paper, architects rely on battle-tested reference architectures developed by Google Cloud engineering. [1] [2]

Whether building an e-commerce platform, a real-time IoT ingestion engine, or an enterprise SaaS product, understanding core structural patterns ensures high availability, security isolation, and horizontal scalability by default. [1] [2]

Core Enterprise Architectural Patterns
  • Three-Tier Web Architecture: Presentation (Cloud CDN / LB), Logic (Cloud Run / GKE), and Persistence (Cloud SQL / Spanner). [1] [2]
  • Event-Driven Microservices: Ingestion via Pub/Sub, processing via Cloud Tasks & Eventarc, asynchronous decoupling. [1] [2]
  • Multi-Region Active-Active: Stateless compute running concurrently in 2+ regions fronted by Global External Application LB. [1] [2]
  • Shared VPC Enterprise Landing Zone: Central networking hub project hosting Shared VPC subnets, connecting spoke projects with strict IAM separation. [1] [2]

Foundation references: Google Cloud Architecture Center · Google Cloud Architecture Framework

The Pain

Reference Architectures & Enterprise Design Patterns becomes risky when teams treat Three-tier web application as a checkbox instead of a boundary with an owner, evidence, and recovery path. [1] [2]

The Idea in One Paragraph

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Decoupling & Statelessness

Compute nodes must remain strictly stateless. Session state, user carts, and transient uploads must be stored in Redis (Memorystore) or object storage (Cloud Storage). [1] [2]

Layer 2 — Practitioner: Multi-Region Active-Active vs Active-Passive

Active-active routes live traffic to both regions simultaneously, offering near-zero RTO. Active-passive keeps a warm or cold standby region, requiring DNS or LB cutover during regional disaster. [1] [2]

Layer 3 — Architect: Multi-Tenant SaaS Isolation Patterns

Isolating tenants by GCP project (highest isolation, compliance-friendly), by Kubernetes namespace (moderate isolation, high resource density), or by row-level database security tags. [1] [2]

Layer 4 — Staff: Anti-Pattern Detection & Eradication

Identifying anti-patterns: chatty synchronous cross-region database queries, monolithic shared databases across autonomous services, and missing circuit breakers. [1] [2]

Technical references: Google Cloud Architecture Center · Google Cloud Architecture Framework

The scope of Reference Architectures & Enterprise Design Patterns is set by Three-tier web application. Separate the control-plane decision from the runtime path, and state which organization, project, region, zone, or resource owns the boundary. [1] [2]

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic: [1] [2]

Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation. [1] [2]

D2 — Request & Control Flow (Runtime Ingress Lens)

4 Practice Exercise

Practice Exercise: Anti-Pattern Identification

Review the following architecture: "A mobile app connects directly to a single Compute Engine VM public IP running MySQL, Redis, and Python Django in us-central1-a. Nightly backups are written to the root disk."

List 4 critical architectural flaws and provide the modern GCP reference architecture replacement for each.

Remediation Solution

  1. Single Point of Failure (SPOF): Replace single VM with a Regional Managed Instance Group (MIG) or Cloud Run behind an External Application Load Balancer.
  2. Co-located State & Monolith: Externalize MySQL to Cloud SQL Regional HA and Redis to Memorystore.
  3. Public IP Direct Ingress: Place compute in private subnets with no public IPs; use Cloud NAT for egress and Load Balancer with Cloud Armor for ingress.
  4. Local Root Disk Backups: Store automated backups and point-in-time recovery archives in Cloud Storage with cross-region dual-region replication.
