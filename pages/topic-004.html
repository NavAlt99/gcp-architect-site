Cloud Concepts & Operating Models

1 Real-World Explanation

The Situation: The Foundation of Cloud Architecture

When Brightloaf Bakery moved to Google Cloud, management initially treated cloud infrastructure like a leased corporate datacenter. They bought giant oversized virtual machines (scaling vertically), manually scheduled weekly backups, and expected Google support to patch their WordPress PHP vulnerabilities. When their database instance ran out of disk space, the site crashed. They realized they were paying cloud prices while inheriting legacy datacenter fragility.

The Three Foundational Cloud Truths
  • Everything Fails All the Time: Design systems assuming VMs will be preempted, zones will fail, and network packets will drop. Build autohealing into every tier.
  • Scale Out, Not Up: Horizontal elasticity (adding small identical compute units) provides higher availability and lower cost than buying massive multi-core single instances.
  • Externalize State: Stateless application layers can scale to zero or surge to thousands of instances instantaneously. Keep state in durable, managed data stores (Cloud SQL, Spanner, Cloud Storage).

The Pain

Without a deliberate Cloud Concepts & Operating Models design, Brightloaf can see slow pages, failed orders, surprise spend, audit gaps, or a deployment that requires a weekend of manual work.

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Service Models (IaaS, PaaS, FaaS, SaaS)

Model GCP Services What Customer Manages What Google Manages
IaaS (Infrastructure as a Service) Compute Engine, VPC, Persistent Disk OS patching, security updates, firewall rules, middleware, application code. Physical hardware, hypervisor, datacenter cooling, power, physical networking.
PaaS (Platform as a Service) App Engine, Cloud SQL, GKE Autopilot Application code, database schema, data access policies. OS provisioning, kernel updates, database engine patching, high availability failover.
FaaS / Serverless Cloud Run, Cloud Run functions Container image or function code, trigger bindings. Zero-to-N autoscaling, routing, concurrency multiplexing, container sandbox.

Layer 2 — Practitioner: The Shared Responsibility Security Matrix

Google secures the cloud; the customer secures what they put in the cloud. Customer is always 100% responsible for:

  • IAM roles, service account keys, and credential rotation.
  • Data classification, bucket access controls (avoiding allUsers).
  • VPC network topologies, private subnets, and firewall allow/deny rules.
  • Application code dependencies and software supply chain vulnerabilities.

Layer 3 — Architect: Availability Zones & Regions Selection

A Google Cloud Region is an independent geographic area with at least three Zones separated by kilometers to prevent correlated physical disaster while maintaining sub-millisecond inter-zone latency.

  • Zonal Resource: Compute Engine instance, zonal Persistent Disk (fails if zone fails).
  • Regional Resource: Regional MIG, Cloud SQL HA, Cloud Storage regional bucket (survives single zone loss).
  • Multi-Regional / Global Resource: Global External ALB, Cloud Spanner, Cloud Storage multi-region, Cloud DNS (survives entire region loss).

Layer 4 — Staff: Disaster Recovery RTO & RPO Engineering

SLA & Failure Impact Table
Scope Failure Blast Radius Architectural Mitigation SLA Objective
Instance Crash Single VM running application Managed Instance Group (MIG) with Autohealing health checks. 99.9% single VM with SSD.
Zonal Datacenter Loss All instances & disks in zone us-central1-a Regional MIG spread across 3 zones + Regional Persistent Disks. 99.99% across zones in region.
Regional Fiber Sever / Natural Disaster Entire region us-east1 offline Multi-region Cloud Spanner + Global ALB with cross-region failover. 99.999% global multi-region.

Scope and planes

The resource model for Cloud Concepts & Operating Models must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Architect trade-off table

ChoiceOperational burdenScaling/consistencyChoose when
Managed optionLower toil, less controlPlatform-definedMinimize undifferentiated operations.
Self-managed optionHigher toil, more controlTeam-definedSpecific runtime or portability constraints matter.
Alternative serviceDifferent cost modelDifferent failure domainIts native data or traffic model fits better.

Choose the managed option when operational simplicity dominates; choose self-managed when control is required; avoid either while requirements remain ambiguous.

Hidden dependencies and day-2 operations

Review DNS, IAM, metadata access, quotas, Google APIs, upgrades, capacity changes, migration off the service, and deprecation risk. Keep ownership, escalation, and landing-zone guardrails explicit.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Question Answered: Where do execution and security boundaries lie?

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.

4 Practice Exercise

Practice Exercise: Calculating Composite Availability SLA

Brightloaf Bakery designs an e-commerce checkout architecture with three sequential dependencies:

  1. Global External HTTPS Load Balancer: 99.99% SLA
  2. Compute Engine Regional MIG in us-west1: 99.95% SLA
  3. Cloud SQL PostgreSQL Single-Instance (Non-HA): 99.90% SLA

Tasks:

  • Calculate the composite end-to-end SLA for the system (Formula: SLA_total = SLA_1 * SLA_2 * SLA_3).
  • Convert the resulting SLA into maximum allowed downtime per month (30 days = 43,200 minutes).
  • State the single architectural change required to raise the database availability to 99.95%.

Worked Solution

1. Composite SLA Calculation:

SLA_total = 0.9999 * 0.9995 * 0.9990 = 0.9984004995 -> 99.84%

2. Maximum Allowed Downtime:

Allowed Downtime = (1 - 0.9984) * 43,200 minutes = 0.0016 * 43,200 = 69.12 minutes/month

3. Required Architecture Upgrade: Upgrade Cloud SQL from Single-Instance to Regional High Availability (HA) with synchronous standby in a second zone. This raises the database SLA from 99.90% to 99.95%.
