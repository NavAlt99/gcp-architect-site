Cloud Concepts & Operating Models

1 Real-World Explanation

The Situation: The Foundation of Cloud Architecture

When Brightloaf Bakery moved to Google Cloud, management initially treated cloud infrastructure like a leased corporate datacenter. They bought giant oversized virtual machines (scaling vertically), manually scheduled weekly backups, and expected Google support to patch their WordPress PHP vulnerabilities. When their database instance ran out of disk space, the site crashed. They realized they were paying cloud prices while inheriting legacy datacenter fragility. [1] [2]

The Three Foundational Cloud Truths
  • Everything Fails All the Time: Design systems assuming VMs will be preempted, zones will fail, and network packets will drop. Build autohealing into every tier. [1] [2]
  • Scale Out, Not Up: Horizontal elasticity (adding small identical compute units) provides higher availability and lower cost than buying massive multi-core single instances. [1] [2]
  • Externalize State: Stateless application layers can scale to zero or surge to thousands of instances instantaneously. Keep state in durable, managed data stores (Cloud SQL, Spanner, Cloud Storage). [1] [2]

Layer 1 — Foundation: Service Models (IaaS, PaaS, FaaS, SaaS)

Model GCP Services What Customer Manages What Google Manages
IaaS (Infrastructure as a Service) Compute Engine, VPC, Persistent Disk OS patching, security updates, firewall rules, middleware, application code. Physical hardware, hypervisor, datacenter cooling, power, physical networking.
PaaS (Platform as a Service) App Engine, Cloud SQL, GKE Autopilot Application code, database schema, data access policies. OS provisioning, kernel updates, database engine patching, high availability failover.

Layer 2 — Practitioner: The Shared Responsibility Security Matrix

Google secures the cloud; the customer secures what they put in the cloud. Customer is always 100% responsible for: [1] [2]

  • IAM roles, service account keys, and credential rotation. [1] [2]
  • Data classification, bucket access controls (avoiding allUsers). [1] [2]
  • VPC network topologies, private subnets, and firewall allow/deny rules. [1] [2]
  • Application code dependencies and software supply chain vulnerabilities. [1] [2]

Layer 3 — Architect: Availability Zones & Regions Selection

A Google Cloud Region is an independent geographic area with at least three Zones separated by kilometers to prevent correlated physical disaster while maintaining sub-millisecond inter-zone latency. [1] [2]

  • Zonal Resource: Compute Engine instance, zonal Persistent Disk (fails if zone fails). [1] [2]
  • Regional Resource: Regional MIG, Cloud SQL HA, Cloud Storage regional bucket (survives single zone loss). [1] [2]
  • Multi-Regional / Global Resource: Global External ALB, Cloud Spanner, Cloud Storage multi-region, Cloud DNS (survives entire region loss). [1]

4 Practice Exercise

Practice Exercise: Calculating Composite Availability SLA

Brightloaf Bakery designs an e-commerce checkout architecture with three sequential dependencies:

  1. Global External HTTPS Load Balancer: 99.99% SLA
  2. Compute Engine Regional MIG in us-west1: 99.95% SLA
  3. Cloud SQL PostgreSQL Single-Instance (Non-HA): 99.90% SLA

Tasks:

  • Calculate the composite end-to-end SLA for the system (Formula: SLA_total = SLA_1 * SLA_2 * SLA_3).
  • Convert the resulting SLA into maximum allowed downtime per month (30 days = 43,200 minutes).
  • State the single architectural change required to raise the database availability to 99.95%.

Worked Solution

1. Composite SLA Calculation:

SLA_total = 0.9999 * 0.9995 * 0.9990 = 0.9984004995 -> 99.84%

2. Maximum Allowed Downtime:

Allowed Downtime = (1 - 0.9984) * 43,200 minutes = 0.0016 * 43,200 = 69.12 minutes/month

3. Required Architecture Upgrade: Upgrade Cloud SQL from Single-Instance to Regional High Availability (HA) with synchronous standby in a second zone. This raises the database SLA from 99.90% to 99.95%.
