Virtualization and Containers: From Hypervisors to Kubernetes

Understanding the isolation boundary: Type-1/Type-2 hypervisors, Linux cgroups & namespaces, container image layers, and foundational Kubernetes runtime objects.

1 Real-World Explanation

The Situation: Scaling From Monolithic VMs to Container Fleets

As Brightloaf Bakery introduced online seasonal ordering, spinning up full Compute Engine virtual machines took 3 to 5 minutes per instance. During sudden traffic spikes, demand overwhelmed the existing servers before new instances could complete boot sequences. Furthermore, engineers suffered from "it worked on my laptop" syndrome, as differing local Python versions broke production deployments. By containerizing workloads using Docker OCI standards and preparing for Google Kubernetes Engine (GKE), Brightloaf reduced deployment spin-up times to sub-second windows with bit-for-bit environment parity. [1]

The Mental Model: VM vs Container Isolation
  • Virtual Machines: Virtualize the underlying hardware. Each VM runs a full guest operating system, kernel, and system services. Strongest security boundary, but heavy footprint. [1] [2]
  • Containers: Virtualize the operating system. Each container is a group of host processes isolated by Linux kernel primitives (cgroups and namespaces). Extremely fast and lightweight, but sharing the host kernel. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Linux Namespaces and Control Groups

Containers are not hardware emulations; they are standard Linux processes running with restricted views: [1] [2]

  • PID Namespace: Isolates process IDs; the container process believes it is PID 1. [1] [2]
  • Net Namespace: Provides an independent virtual network interface, routing table, and port bindings. [1]
  • Mount Namespace: Presents a private filesystem mount tree based on union container layers. [1] [2]
  • cgroups (Control Groups): Enforces strict CPU, memory, IO, and network bandwidth quotas. [1] [2]

Layer 2 — Practitioner: Multi-Stage Container Image Hygiene

Never package build compilers, package managers, or SDKs into production container images. Use multi-stage Docker builds with Google Distroless base images: [1] [2]

# Build Stage
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .

# Production Distroless Stage
FROM gcr.io/distroless/nodejs20-debian12
WORKDIR /app
COPY --from=build /app /app
USER nonroot:nonroot
EXPOSE 8080
CMD ["server.js"]

Layer 3 — Architect: Container Sandboxing & Security Boundaries

Because containers share the host Linux kernel, multi-tenant untrusted code requires hardened isolation: [1] [2]

  • GKE Sandbox (gVisor): Implements a user-space kernel that intercepts and filters application system calls, preventing host kernel exploits. [1] [2]
  • Compute Engine Confidential VMs: Employs AMD SEV memory encryption to protect data in memory from hypervisor inspection. [1] [2]

4 Practice Exercise

Practice Exercise: Designing a Kubernetes Pod Manifest with Liveness Probes

Write a production Kubernetes Pod specification for the brightloaf-order-service satisfying these constraints:

  • Image: us-docker.pkg.dev/brightloaf-prod/apps/orders:v1.2.0
  • Runs as non-root user (UID 10001) with a read-only root filesystem.
  • Enforces resource requests (250m CPU, 256Mi memory) and limits (500m CPU, 512Mi memory).
  • Configures an HTTP liveness probe on path /healthz, port 8080, with a 5-second timeout.

Worked Solution

apiVersion: v1
kind: Pod
metadata:
  name: brightloaf-order-service
  labels:
    app.kubernetes.io/name: orders
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
  containers:
  - name: order-api
    image: us-docker.pkg.dev/brightloaf-prod/apps/orders:v1.2.0
    securityContext:
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 10
      timeoutSeconds: 5
      failureThreshold: 3
