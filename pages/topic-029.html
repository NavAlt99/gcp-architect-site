SRE Concepts: SLIs, SLOs, Error Budgets & The Four Golden Signals

Site Reliability Engineering principles: Service Level Indicators (SLIs), Service Level Objectives (SLOs), error budget release gating, the Four Golden Signals (Latency, Traffic, Errors, Saturation), and blameless post-mortems.

1 Real-World Explanation

The Situation: Resolving the Conflict Between Dev and Ops

In traditional software teams, developers are rewarded for shipping features quickly, while operations engineers are rewarded for keeping systems stable. This creates an adversarial relationship: Dev wants change, Ops fears change. [1] [2]

Google Site Reliability Engineering (SRE) resolves this structural conflict using Service Level Objectives (SLOs) and Error Budgets: [1] [2]

The SRE Vocabulary: SLI, SLO, SLA
  • SLI (Service Level Indicator): A quantifiable metric of service performance:
    SLI = (Good Events / Total Valid Events) × 100%. [1] [2]
  • SLO (Service Level Objective): An internal reliability target agreed upon by Product and Engineering (e.g., 99.9% of requests over 30 rolling days). [1] [2]
  • SLA (Service Level Agreement): A commercial contract with external customers specifying financial consequences or credits if violated. (Rule: SLO > SLA). [1] [2]
  • Error Budget: The room for unreliability: Error Budget = 100% - SLO. For a 99.9% SLO, the error budget is 0.1%. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: The Four Golden Signals

Focus monitoring on the 4 Golden Signals: Latency (time taken to serve a request), Traffic (demand / RPS / concurrent sessions), Errors (explicit failures like HTTP 5xx, or misformed responses), and Saturation (fraction of constrained resources used, e.g. memory or thread pool saturation). [1] [2]

Layer 2 — Practitioner: Multi-Window Multi-Burn-Rate Alerts

Do not alert on static thresholds (e.g. CPU > 80%). Alert on Error Budget Burn Rate: a 14.4x burn rate consumes 2% of your monthly budget in 1 hour; this requires immediate paging. A 2x burn rate consumes 10% in 36 hours; send a ticket. [1] [2]

Layer 3 — Architect: Error Budget Policies & Release Freezes

Establish a binding social contract: when the error budget is exhausted, developers stop shipping new product features and focus 100% of their sprints on reliability, bug fixes, and test automation. [1] [2]

Layer 4 — Staff: Blameless Post-Mortems & Eliminating Toil

When incidents occur, conduct blameless post-mortems focused on systemic flaws, not human mistakes. SRE teams cap operational toil (manual repetitive tasks) at 50%, dedicating the remaining time to engineering automation. [1] [2]

4 Practice Exercise

Hands-On Demo: Creating an SLO in Cloud Monitoring

Define an availability SLO using the Google Cloud CLI or Monitoring API.

# 1. List available monitored services
gcloud monitoring services list

# 2. Create a service for an App/Cloud Run service
gcloud monitoring services create \
    --service-id="checkout-service" \
    --display-name="Checkout Microservice"

# 3. Define an Availability SLO (99.9% over a 28-day rolling window)
# slo.json:
# {
#   "displayName": "99.9% - High Availability Checkout",
#   "goal": 0.999,
#   "rollingPeriod": "2419200s",
#   "serviceLevelIndicator": {
#     "basicSli": {
#       "availability": {}
#     }
#   }
# }
gcloud monitoring services slos create \
    --service="checkout-service" \
    --config-from-file="slo.json"
