Serverless Compute: Cloud Run, Functions, and Workflows

Modern serverless system design: Cloud Run services vs jobs, concurrency tuning, cold start mitigation, event-driven triggers with Eventarc, and stateful orchestration via Workflows.

1 Real-World Explanation

The Situation: The Default Choice for Modern APIs

For modern web applications, microservices, and event processing, Cloud Run is Google Cloud's default compute recommendation. Unlike traditional serverless that forced proprietary runtimes, Cloud Run executes any standard OCI container image listening on an HTTP port. It provides genuine scale-to-zero economics (pay nothing when idle) and rapid horizontal scaling to thousands of instances. [1] [2]

Cloud Run Services vs Cloud Run Jobs
  • Cloud Run Services: Long-running HTTP endpoints listening for web requests, gRPC calls, or Pub/Sub push messages. Autoscales based on incoming request concurrency. [1] [2]
  • Cloud Run Jobs: Runs tasks to completion (e.g. nightly database backups, batch data processing, machine learning inference jobs). Does not listen on an HTTP port; terminates when task finishes. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Concurrency vs One-Request-Per-Instance

Unlike AWS Lambda (which executes strictly 1 request per container instance), Cloud Run handles up to 1000 concurrent requests per instance (default 80). Tuning concurrency significantly reduces costs and cold-start frequency. [1] [2]

Layer 2 — Practitioner: Connecting to Private VPC Resources

By default, Cloud Run has no access to private RFC 1918 VPC networks. Use Direct VPC Egress (or Serverless VPC Access connectors) to allow Cloud Run to query private Cloud SQL databases, Redis Memorystore, and internal microservices securely. [1] [2]

Layer 3 — Architect: Event-Driven Architectures with Eventarc

Build decoupled event pipelines using Eventarc: capture Cloud Storage bucket uploads, Cloud Audit Log events, or custom Pub/Sub messages and route them directly to Cloud Run microservices in CloudEvents format. [1] [2]

Layer 4 — Staff: Traffic Splitting & Blue/Green Deployments

Every deployment to Cloud Run creates an immutable Revision. Staff engineers use revision tags and gradual traffic splitting (e.g. 5% to canary, 95% to current) to execute zero-downtime rollouts with instant rollback capabilities. [1] [2]
