Application & Supply-Chain Security: Binary Authorization & SLSA

Hardening the software delivery pipeline: Secure SDLC, Artifact Analysis vulnerability scanning, Binary Authorization cryptographic attestations, SLSA framework levels, and Distroless containers.

1 Real-World Explanation

The Situation: The Rise of Software Supply Chain Attacks

In modern software delivery, attackers rarely attack hardened production firewalls directly. Instead, they poison the software supply chain: tampering with open-source dependencies, compromising CI/CD pipelines, or pushing unauthorized container images directly to registries. [1] [2]

Google Cloud provides an end-to-end framework adhering to SLSA (Supply-chain Levels for Software Artifacts) to guarantee software integrity from source code to production deployment. [1] [2]

The Three Pillars of Cloud Supply Chain Security
  • Artifact Analysis: Automated container vulnerability scanning in Artifact Registry for OS package CVEs and language dependencies (Java, Node, Python, Go). [1] [2]
  • Binary Authorization: A deploy-time admission control security policy on GKE and Cloud Run that ensures only trusted, cryptographically signed container images can run. [1] [2]
  • Distroless & Hardened Images: Stripping package managers, shells, and debugging tools from containers to minimize attack surfaces and CVE exposure. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Distroless Containers & Non-Root Execution

Never run containers as root. Build images using Google's open-source Distroless base images: they contain only your compiled application and runtime dependencies, without a bash shell or package manager. [1] [2]

Layer 2 — Practitioner: Automated Vulnerability Scanning in Artifact Registry

Artifact Analysis scans every pushed container image against the national vulnerability database (NVD). Set policy rules that block promotion of any image containing unresolved CRITICAL or HIGH CVEs. [1] [2]

Layer 3 — Architect: Binary Authorization with Cloud KMS Attestations

Establish multiple attestor gates: (1) Unit Tests Passed, (2) Vulnerability Scan Clear, (3) Security Lead Approved. Cloud KMS signs an attestation for each gate. GKE admission controllers require all signatures before launching the pod. [1] [2]

Layer 4 — Staff: Software Bill of Materials (SBOM) & SLSA Level 3

Staff architects automate SBOM generation for every build, providing complete provenance tracing back to exact Git commit hashes, builder identities, and dependency manifests. [1] [2]

4 Practice Exercise

Hands-On Demo: Enabling Binary Authorization on a GKE Cluster

Enforce deploy-time verification of container signatures on your Kubernetes workloads.

# 1. Enable Binary Authorization on a GKE cluster
gcloud container clusters update my-secure-cluster \
    --region=us-central1 \
    --binauthz-evaluation-mode=PROJECT_SINGLETON_POLICY_ENFORCE

# 2. View current Binary Authorization policy
gcloud container binauthz policy export > policy.yaml

# 3. Policy snippet requiring attestors (policy.yaml):
# defaultAdmissionRule:
#   evaluationMode: REQUIRE_ATTESTATION
#   enforcementMode: ENFORCING
#   requireAttestationsBy:
#     - projects/PROJECT_ID/attestors/build-attestor

# 4. Import updated policy
gcloud container binauthz policy import policy.yaml
