Messaging and Integration: Pub/Sub, Cloud Tasks, and Eventarc

Asynchronous microservice decoupling: Cloud Pub/Sub publish-subscribe mechanics, push vs pull subscriptions, message ordering, dead-letter topics, Cloud Tasks rate-limiting, and Workflows orchestration.

1 Real-World Explanation

The Situation: Decoupling Distributed Microservices

In monolithic systems, services invoke each other synchronously via HTTP or database locks. If the email notification service slows down, the entire checkout process times out. By introducing Cloud Pub/Sub as an asynchronous message bus, producers publish events without waiting for consumers, achieving true architectural decoupling and smoothing traffic spikes. [1]

Pub/Sub vs Cloud Tasks: When to Use Which?
  • Cloud Pub/Sub (Publish-Subscribe): 1-to-many message distribution. Publisher does not know or care who is listening. Best for event streaming, analytics pipelines, and decoupled microservices. [1]
  • Cloud Tasks (Task Queues): 1-to-1 asynchronous invocation. Explicit target endpoint, strict rate-limiting (e.g. max 50 requests/sec to legacy API), scheduled execution in the future, and task deduplication. [1]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Push vs Pull Subscriptions

  • Pull Subscriptions: Consumers poll Pub/Sub for messages and send explicit ACKs. Best for high-volume batch processing (Dataflow, GKE worker pools). [1] [2]
  • Push Subscriptions: Pub/Sub sends HTTPS POST requests directly to consumer endpoints (Cloud Run, webhooks). Best for serverless scale-to-zero architectures. [1]

Layer 2 — Practitioner: Delivery Guarantees & Dead-Letter Topics

Pub/Sub guarantees at-least-once delivery. Consumers must be designed to be idempotent (handling duplicate messages safely). Configure a Dead-Letter Topic with a maximum delivery attempts threshold (e.g. 5) to quarantine corrupt poison-pill messages. [1]

Layer 3 — Architect: Message Ordering & Retention

By default, Pub/Sub does not guarantee strict FIFO ordering. To preserve sequence (e.g. bank account deposits and withdrawals), enable Message Ordering Keys. Pub/Sub retains unacknowledged messages for up to 7 days (or replay acknowledged messages via seek). [1]

Layer 4 — Staff: Exactly-Once Processing with Dataflow

For financial transactions where duplicates cannot be tolerated, combine Pub/Sub with Cloud Dataflow (Apache Beam) to achieve cryptographically verified exactly-once processing semantics. [1] [2]
