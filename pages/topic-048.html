Case Study: TerramEarth — IoT Fleet, Bigtable & Predictive Maintenance

1 Real-World Explanation

Case Profile: TerramEarth

Company Background: TerramEarth designs and manufactures heavy agricultural and mining equipment. They have over 20 million vehicles deployed globally. 200,000 vehicles have continuous cellular connectivity, while the remaining 19.8 million vehicles upload sensor data only when they return to maintenance depots with Wi-Fi. [1] [2]

TerramEarth Requirements Breakdown
  • Business Goals: Predict equipment failures before they happen (predictive maintenance) to prevent costly farm downtime; sell autonomous operational insights to equipment operators. [1] [2]
  • Technical Requirements: Ingest streaming real-time alerts from 200,000 cellular vehicles (200 sensors at 1 Hz = millions of events/sec); ingest 50 GB daily Wi-Fi batch files from 19.8M vehicles; sub-10ms query latency for operational telemetry dashboards. [1] [2]
  • Core Watchpoint: Dual Ingestion Strategy. Real-time streaming (Pub/Sub) vs massive asynchronous batch file uploads (Cloud Storage + Storage Transfer Service). [1]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: The Dual-Speed Ingestion Architecture

Segregate workloads: (1) Speed Layer (Cellular): Vehicles publish real-time alerts directly to Cloud Pub/Sub; (2) Batch Layer (Wi-Fi): Vehicles dump compressed binary sensor files to regional Cloud Storage buckets when connected to depot Wi-Fi. [1]

Layer 2 — Practitioner: Cloud Bigtable for High-Throughput Time-Series

Sensor telemetry is time-series data with extreme write volume. Cloud Bigtable provides linear horizontal scalability with sub-10ms read/write latency. Design row keys properly: vehicle_id#timestamp_reversed to prevent hotspotting on a single node. [1] [2]

Layer 3 — Architect: Dataflow ETL & BigLake Analytics

Use Cloud Dataflow to execute unified batch and streaming pipelines. Dataflow deduplicates telemetry events, parses binary formats, and writes operational metrics to Bigtable while sinking curated tables to BigQuery via BigLake. [1] [2]

Layer 4 — Staff: Vertex AI Predictive Maintenance Pipelines

Train anomaly detection and regression models on Vertex AI using historical sensor degradation curves. When real-time Bigtable telemetry matches a pre-failure signature, trigger an automated maintenance alert dispatching replacement parts to the farm. [1] [2]

4 Practice Exercise

Practice Exercise: TerramEarth Row Key Design Drill

In Cloud Bigtable, sequential row keys (e.g. timestamp#sensor_id) cause a critical anti-pattern known as hotspotting, where 100% of writes hit a single Bigtable tablet server while other nodes remain idle.

Design an optimal row key schema for TerramEarth's 20 million vehicles to ensure uniform distribution across all Bigtable cluster nodes.

Optimal Row Key Schema

Recommended Schema: <vehicle_id>#<sensor_type>#<reversed_timestamp>

  • vehicle_id prefix: Distributes writes across different lexicographical keyspaces and nodes evenly, preventing sequential write hotspotting.
  • sensor_type: Allows targeted scanning of specific telemetry metrics (e.g. engine temperature).
  • reversed_timestamp (Long.MAX_VALUE - timestamp): Ensures the most recent telemetry readings appear first during range scans, accelerating real-time dashboard queries.
