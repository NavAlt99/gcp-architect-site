Compute Engine: VMs, Disks, and Managed Instance Groups

Deep dive into Google Compute Engine: machine families (General-purpose, Compute, Memory, Accelerator), Persistent Disk topologies, Managed Instance Groups (MIGs), Autohealing, and Spot VM economics.

1 Real-World Explanation

The Situation: Enterprise Infrastructure as a Service

Compute Engine provides secure, high-performance virtual machines running on Google's global infrastructure. It caters to workloads requiring full OS control, legacy enterprise software (SAP, Oracle, Windows Server), high-performance computing (C3/H3), or custom kernel extensions. [1] [2]

Compute Engine Machine Families
  • General-Purpose (E2, N2, N4, C3): Best price-performance for web applications, databases, and microservices. E2 uses dynamic resource sharing; N2 offers predictable performance; C3 features Google's custom Titanium IPU. [1] [2]
  • Compute-Optimized (C2, C2D, H3): Highest per-core performance for gaming servers, video rendering, and batch processing. [1] [2]
  • Memory-Optimized (M2, M3): Giant RAM capacity (up to 12 TB memory) for SAP HANA and large in-memory databases. [1] [2]
  • Accelerator-Optimized (A2, A3, G2): Equipped with NVIDIA H100/L4 GPUs for AI training and LLM inference. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Boot Disks & Persistent Storage

VM root disks are network-attached block devices (Persistent Disks), not physical hard drives inside the server rack. Types include Standard HDD, Balanced SSD (pd-balanced), Performance SSD (pd-ssd), and Local SSD (ephemeral, physically attached, ultra-low latency, wiped on instance stop). [1] [2]

Layer 2 — Practitioner: Managed Instance Groups (MIGs)

A MIG uses an Instance Template to manage a homogeneous fleet of VMs. Key capabilities: [1] [2]

  • Autoscaling: Scales out based on target CPU utilization (e.g. 60%), Load Balancer utilization, or custom Cloud Monitoring metrics. [1] [2]
  • Autohealing: Dedicated health check probes application endpoint. If unresponsive for failure threshold, the MIG tears down the unhealthy VM and provisions a fresh replacement. [1] [2]
  • Rolling Updates: Deploys new instance templates gradually with maxSurge and maxUnavailable controls. [1] [2]

Layer 3 — Architect: Regional vs Zonal Resiliency

Always deploy Regional MIGs for production. Regional MIGs balance instances evenly across 3 zones. If an entire datacenter zone suffers catastrophic failure, the remaining two zones absorb traffic while the autoscaler replenishes capacity. [1] [2]

Layer 4 — Staff: Spot VMs & Live Migration Internals

Google Compute Engine performs Live Migration: when physical host hardware requires maintenance, Google migrates running VMs to a new physical host without shutting down the OS or dropping TCP connections. For fault-tolerant batch workloads, Spot VMs offer 60-91% discounts with the caveat that Google may preempt them with 30-second notice. [1] [2]

4 Hands-On Demo

Hands-On Demo: Creating an Autohealing Regional Managed Instance Group
# 1. Create instance template with health endpoint
gcloud compute instance-templates create web-template   --region=us-west1   --machine-type=e2-medium   --metadata=startup-script='#! /bin/bash
    apt-get update && apt-get install -y nginx
    echo "Healthy" > /var/www/html/healthz'

# 2. Create health check
gcloud compute health-checks create http web-health-check   --request-path=/healthz --port=80

# 3. Create regional MIG with autohealing
gcloud compute instance-groups managed create web-mig   --region=us-west1   --template=web-template   --size=3   --health-check=web-health-check   --initial-delay=120
