1 Real-World Explanation

The Situation: The Danger of Ambiguous Architecture Diagrams

Almost every failed cloud deployment can be traced back to an ambiguous diagram. A white box labeled "API" connected by an unlabelled arrow to another white box labeled "Database" hides dozens of critical questions: [1] [2]

  • What protocol is used? (HTTPS, gRPC, raw TCP?) [1] [2]
  • Is the connection authenticated, encrypted in transit (TLS 1.3), or traversing the public internet? [1]
  • What happens when the database is unreachable? (Retry? Circuit break? Failover?) [1] [2]
  • Which GCP project, VPC, region, and security perimeter does each service belong to? [1] [2]

Professional cloud architects use structured methodologies like the C4 Model and diagrammatic standards to communicate unambiguous technical designs. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: The C4 Model (Zoom Levels)

Created by Simon Brown, C4 provides 4 zoom levels: Context (people and systems), Containers (deployable units like Cloud Run, GKE pods, Cloud SQL), Components (internal software modules), and Code (class diagrams). [1] [2]

Layer 2 — Practitioner: Network & Data Flow Standards

Every arrow must have a clear direction, explicit label, and protocol (e.g., HTTPS / OAuth 2.0 (Port 443)). Group components into clear visual perimeters: External, VPC, Regional Subnet, and Database Tier. [1]

Layer 3 — Architect: Sequence Diagrams for Failure Scenarios

Static diagrams only show the happy path. Architects produce UML sequence diagrams illustrating failure scenarios: timeouts, primary zone crashes, circuit breakers tripping, and health check rerouting. [1] [2]

Layer 4 — Staff: Diagrams as Code (Mermaid & PlantUML)

Storing diagrams as text in Git alongside code. Pull requests update both the Terraform code and the Mermaid diagram simultaneously, preventing documentation drift. [1]

Technical references: C4 model · Google Cloud Architecture Center

Scope and planes

The scope of Diagramming & Documentation: C4 Model & Visual Standards is set by C4 model (context, container, component). Separate the control-plane decision from the runtime path, and state which organization, project, region, zone, or resource owns the boundary. [1] [2]

Practitioner defaults and troubleshooting

Start by verifying Network diagrams with regions, zones, subnets and flows, then inspect the identity, quota, network, logging, and dependency evidence that can invalidate that assumption. [1]

2B — Interactive Architecture Diagrams

Diagram Architectural Scope & Taxonomy: Why These Three Diagrams Exist

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic: [1] [2]

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation. [1] [2]

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging. [1]

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways. [1]
