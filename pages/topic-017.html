Topic 017 Roadmap ID: 2.5 Phase 2 — Core Services Type: service Verified: 2026-09-24

Cloud Load Balancing, Cloud CDN, and Cloud Armor

High-capacity global edge architecture: Global External Application Load Balancers (HTTP/S), Regional L7, L4 Passthrough Network LBs, Cloud CDN caching, and Cloud Armor WAF defense.

On this page
1 Real-World Explanation 2 Technical Discussion 3 Cloud City Analogy 4 Hands-On Demo 5 Knowledge Check 6 Further Reading

1 Real-World Explanation

The Situation: True Global Load Balancing Without Pre-Warming

Unlike traditional load balancers (like AWS ALB) that scale up DNS records and require "pre-warming" before massive traffic spikes, Google Cloud Load Balancing is a software-defined, distributed proxy running on Google Frontends (GFEs). A single Global External Application Load Balancer presents one Anycast IP address to the entire world. It can scale instantly from 0 to 1,000,000+ QPS without any pre-warming or DNS changes.

The Pain

Without a deliberate Cloud Load Balancing, Cloud CDN, and Cloud Armor design, Brightloaf can see slow pages, failed orders, surprise spend, audit gaps, or a deployment that requires a weekend of manual work.

The Idea in One Paragraph

Cloud Load Balancing, Cloud CDN, and Cloud Armor gives one business problem a clear boundary, an observable lifecycle, and an explicit recovery choice. The learner should be able to explain the idea before seeing configuration.

Real-World Examples

  • Retail: a seasonal order spike must not become a checkout outage.
  • Healthcare: a records workflow must preserve privacy and an audit trail.
  • Media or gaming: a bursty workload must scale without making every dependency global.

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Load Balancer Taxonomy

  • Global External Application Load Balancer (L7): HTTP/HTTPS/HTTP2/gRPC. Terminate TLS at edge; URL host and path routing; integrates with Cloud CDN and Cloud Armor.
  • Regional External Application Load Balancer (L7): HTTP/S within a single region for strict data sovereignty compliance.
  • External Passthrough Network Load Balancer (L4): Raw TCP/UDP. Non-proxy, preserves client IP, ultra-high performance Maglev packet forwarding.
  • Internal Application / Network Load Balancer: Private RFC 1918 load balancing between microservice tiers inside the VPC.

Layer 2 — Practitioner: SSL Policies & Google-Managed Certificates

Google Cloud provisions, validates, and auto-renews free SSL certificates via Certificate Manager. Use SSL Policies to restrict cipher suites (e.g. mandate TLS 1.3 and ban insecure CBC ciphers).

Layer 3 — Architect: Cloud Armor WAF & Edge Caching

Protect origins from Layer 7 attacks using Cloud Armor: preconfigured rules defend against SQLi, XSS, and LFI. Enable Cloud CDN on backend buckets or services to serve static web assets directly from edge caches with sub-10ms response times.

Layer 4 — Staff: Cross-Region Overflow & Failover Mechanics

Global ALBs monitor backend capacity (target utilization or rate). When the us-west1 cluster reaches 100% capacity during a local flash sale, the load balancer automatically overflows excess traffic to us-central1 without returning HTTP 503 errors.

Scope and planes

The resource model for Cloud Load Balancing, Cloud CDN, and Cloud Armor must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Question Answered: Where do execution and security boundaries lie?

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.

4 Hands-On Demo

Hands-On Demo: Creating a Cloud Armor Security Policy
# 1. Create Cloud Armor policy
gcloud compute security-policies create block-bad-actors   --description="Block SQLi and rate limit bots"

# 2. Add preconfigured OWASP SQL injection rule
gcloud compute security-policies rules create 1000   --security-policy=block-bad-actors   --expression="evaluatePreconfiguredExpr('sqli-v33-stable')"   --action=deny-403

# 3. Attach policy to backend service
gcloud compute backend-services update web-backend-service   --global   --security-policy=block-bad-actors
