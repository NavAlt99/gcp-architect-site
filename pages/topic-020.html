Databases: Cloud SQL, Spanner, Firestore, and Bigtable

1 Real-World Explanation

The Situation: Selecting the Right Persistence Engine

Data architecture determines the scalability and reliability ceiling of every cloud system. Google Cloud offers purpose-built databases engineered for distinct operational requirements. For architects, knowing which database to choose and why is heavily tested on the Professional Cloud Architect (PCA) exam. [1] [2]

The Master Database Selection Guide
  • Cloud SQL: Traditional relational (MySQL, PostgreSQL, SQL Server). Best for workloads up to a few terabytes requiring full SQL compatibility and existing ORM support. [1] [2]
  • Cloud Spanner: Enterprise relational with unlimited horizontal scale and 99.999% SLA. ACID compliance with global external consistency. Best for mission-critical banking, global inventory, and massive transactional scale. [1] [2]
  • Firestore: Fully managed serverless NoSQL document database. Real-time synchronization, mobile SDKs, offline support, scale-to-zero. Best for web/mobile apps and user profiles. [1] [2]
  • Cloud Bigtable: Petabyte-scale, ultra-low latency NoSQL wide-column database. Millisecond response times for massive streaming writes (IoT, time-series, financial ticker data). [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Cloud SQL High Availability (HA)

Cloud SQL HA uses Regional Persistent Disks to synchronously replicate data across two zones in the same region. If the primary zone fails, the failover to the standby instance occurs automatically in under 60 seconds without data loss. [1] [2]

Layer 2 — Practitioner: Read Replicas vs Backups

Read replicas offload read queries, but replicas do not protect against data corruption (an accidental DROP TABLE replicates instantly). Always enable Point-In-Time Recovery (PITR) via automated binary logging. [1] [2]

Layer 3 — Architect: Cloud Spanner TrueTime & Key Design

Spanner achieves global transactions without locking bottlenecks using TrueTime (synchronized atomic clocks and GPS receivers in Google datacenters). Critical Spanner Rule: Never use sequential auto-incrementing primary keys; sequential keys create hotspots on single splits. Always use UUIDv4 or bit-reversed keys. [1]

Layer 4 — Staff: Database Migration & CDC with Datastream

Staff architects execute zero-downtime database migrations from on-premises Oracle/PostgreSQL to Google Cloud using Database Migration Service (DMS) and Datastream Change Data Capture (CDC). [1] [2]
