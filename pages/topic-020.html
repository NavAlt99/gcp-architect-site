Databases: Cloud SQL, Spanner, Firestore, and Bigtable

The database decision matrix: Relational vs NoSQL, Cloud SQL HA topologies, Cloud Spanner 99.999% global consistency, Firestore document stores, and Bigtable IoT petabyte scaling.

1 Real-World Explanation

The Situation: Selecting the Right Persistence Engine

Data architecture determines the scalability and reliability ceiling of every cloud system. Google Cloud offers purpose-built databases engineered for distinct operational requirements. For architects, knowing which database to choose and why is heavily tested on the Professional Cloud Architect (PCA) exam.

The Master Database Selection Guide
  • Cloud SQL: Traditional relational (MySQL, PostgreSQL, SQL Server). Best for workloads up to a few terabytes requiring full SQL compatibility and existing ORM support.
  • Cloud Spanner: Enterprise relational with unlimited horizontal scale and 99.999% SLA. ACID compliance with global external consistency. Best for mission-critical banking, global inventory, and massive transactional scale.
  • Firestore: Fully managed serverless NoSQL document database. Real-time synchronization, mobile SDKs, offline support, scale-to-zero. Best for web/mobile apps and user profiles.
  • Cloud Bigtable: Petabyte-scale, ultra-low latency NoSQL wide-column database. Millisecond response times for massive streaming writes (IoT, time-series, financial ticker data).

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Cloud SQL High Availability (HA)

Cloud SQL HA uses Regional Persistent Disks to synchronously replicate data across two zones in the same region. If the primary zone fails, the failover to the standby instance occurs automatically in under 60 seconds without data loss.

Layer 2 — Practitioner: Read Replicas vs Backups

Read replicas offload read queries, but replicas do not protect against data corruption (an accidental DROP TABLE replicates instantly). Always enable Point-In-Time Recovery (PITR) via automated binary logging.

Layer 3 — Architect: Cloud Spanner TrueTime & Key Design

Spanner achieves global transactions without locking bottlenecks using TrueTime (synchronized atomic clocks and GPS receivers in Google datacenters). Critical Spanner Rule: Never use sequential auto-incrementing primary keys; sequential keys create hotspots on single splits. Always use UUIDv4 or bit-reversed keys.

Layer 4 — Staff: Database Migration & CDC with Datastream

Staff architects execute zero-downtime database migrations from on-premises Oracle/PostgreSQL to Google Cloud using Database Migration Service (DMS) and Datastream Change Data Capture (CDC).

Scope and planes

The resource model for Databases: Cloud SQL, Spanner, Firestore, and Bigtable must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Hidden dependencies and day-2 operations

Review DNS, IAM, metadata access, quotas, Google APIs, upgrades, capacity changes, migration off the service, and deprecation risk. Keep ownership, escalation, and landing-zone guardrails explicit.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Diagram Architectural Scope & Taxonomy: Why These Three Diagrams Exist

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic:

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation.

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.
