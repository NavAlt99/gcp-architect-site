Topic 034 Roadmap ID: 5.1 Phase 5 — Security and Compliance Type: service Verified: 2026-09-24

Advanced IAM, Identity Federation & Zero Trust

Next-generation identity architectures: IAM Conditions, Deny Policies, Workload Identity Federation (AWS/GitHub without keys), Privileged Access Manager (PAM), and BeyondCorp Identity-Aware Proxy (IAP).

On this page

1 Real-World Explanation

The Situation: The Hazard of Static Service Account Keys

At Brightloaf Bakery, an engineer committed a service account private key JSON file into a public GitHub repository. Within 15 minutes, automated bots discovered the key and spun up hundreds of GPU instances for cryptomining, generating a $45,000 bill. [1] [2]

Modern cloud security is founded on the Zero Trust model: "Never trust, always verify." Static private keys are an anti-pattern. Using Workload Identity Federation, external systems (GitHub Actions, AWS EC2, GitLab, on-prem Kubernetes) authenticate to Google Cloud using short-lived OpenID Connect (OIDC) tokens with zero secrets to store or rotate. [1] [2]

Advanced IAM Governance Primitives
  • Workload Identity Federation: Exchanging AWS IAM or GitHub OIDC tokens for temporary GCP access tokens via Security Token Service (STS). [1] [2]
  • IAM Conditions: Applying attribute-based access control (ABAC) based on resource tags, IP address, day of week, or time of day. [1] [2]
  • IAM Deny Policies: Hard overrides that take precedence over all grant policies, preventing accidental privilege escalation. [1] [2]
  • Privileged Access Manager (PAM): Just-in-time, temporary privilege elevation with automated workflow approvals. [1] [2]
  • Identity-Aware Proxy (IAP): Context-aware zero-trust access to web apps and SSH/RDP without public IPs or VPNs. [1] [2]

The Pain

Advanced IAM, Identity Federation & Zero Trust becomes risky when teams treat Least privilege, separation of duties, need-to-know as a checkbox instead of a boundary with an owner, evidence, and recovery path. [1] [2]

The Idea in One Paragraph

Advanced IAM, Identity Federation & Zero Trust is a design decision anchored by Least privilege, separation of duties, need-to-know. Connect it to Predefined vs custom roles; IAM Recommender for right-sizing permissions, make the dependency visible, and state what changes when the requirement or failure domain changes. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Eliminating Service Account Keys

Enforce the Organization Policy constraint constraints/iam.disableServiceAccountKeyCreation. Workloads inside GCP use default service accounts or GKE Workload Identity; workloads outside GCP use Workload Identity Federation. [1] [2]

Layer 2 — Practitioner: IAM Conditions & Context-Aware Access

Enforce conditional access: e.g., allow deployment engineers access to production only between 09:00 and 17:00 UTC and only when connecting from corporate IP ranges using CEL expressions. [1] [2]

Layer 3 — Architect: Deny Policies & Principal Access Boundaries

IAM Deny policies act as organizational guardrails. Even if a project owner grants roles/editor to a user, a Deny policy targeting specific permissions (like iam.serviceAccounts.delete) cannot be overridden at the project level. [1] [2]

Layer 4 — Staff: Zero-Trust BeyondCorp Architecture

Replace legacy corporate VPNs with BeyondCorp. IAP verifies user identity, device health, location, and MFA on every single HTTP request before proxying traffic to private internal services. [1] [2]

4 Hands-On Demo

Hands-On Demo: Configuring Workload Identity Federation for GitHub Actions

Set up keyless authentication between GitHub Actions CI/CD and Google Cloud.

# 1. Create a Workload Identity Pool
gcloud iam workload-identity-pools create "github-pool" \
    --location="global" \
    --display-name="GitHub Actions Pool"

# 2. Add an OIDC Provider for GitHub
gcloud iam workload-identity-pools providers create-oidc "github-provider" \
    --workload-identity-pool="github-pool" \
    --location="global" \
    --issuer-uri="https://token.actions.githubusercontent.com" \
    --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository"

# 3. Allow GitHub repository to impersonate a service account
gcloud iam service-accounts add-iam-policy-binding "ci-builder@my-project.iam.gserviceaccount.com" \
    --role="roles/iam.workloadIdentityUser" \
    --member="principalSet://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/github-pool/attribute.repository/my-org/my-repo"
