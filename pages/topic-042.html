Infrastructure as Code: Terraform, GitOps & Config Connector

1 Real-World Explanation

The Situation: The Chaos of "ClickOps"

Provisioning cloud resources manually through the Google Cloud Console ("ClickOps") is an anti-pattern for enterprise workloads. It creates environments that cannot be reproduced, audited, or reliably recovered during a disaster. [1] [2]

Infrastructure as Code (IaC) treats cloud infrastructure with the exact same rigor as application code: written in declarative text files, version-controlled in Git, tested in CI/CD pipelines, and deployed automatically. [1] [2]

Core Terraform Concepts on Google Cloud
  • Declarative Syntax (HCL): You declare what the infrastructure should look like; Terraform calculates the dependency graph and steps needed to reach that state. [1]
  • Remote State in Cloud Storage: Storing terraform.tfstate in an encrypted, versioned GCS bucket with automated locking prevents concurrent execution corruption. [1]
  • Cloud Foundation Toolkit (CFT): Google's enterprise-grade, opinionated, production-ready Terraform modules that adhere to CIS security benchmarks. [1] [2]
  • Config Connector: A Kubernetes operator that allows you to manage Google Cloud resources (VPCs, Cloud SQL, Buckets) natively via Kubernetes Custom Resource Definitions (CRDs). [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Remote State Locking in GCS

Always configure a remote backend in Cloud Storage with Object Versioning enabled. Terraform uses GCS strongly-consistent metadata locking to prevent two engineers from applying changes simultaneously. [1]

Layer 2 — Practitioner: Terraform Modules & Workspaces

Never write monolithic 5,000-line main.tf files. Break infrastructure into reusable modules (modules/vpc, modules/gke, modules/cloudsql). Use workspaces or folder-based environments (environments/dev, environments/prod). [1] [2]

Layer 3 — Architect: Drift Detection & Automated Reconciliation

Manual console changes create "configuration drift". Schedule a daily automated terraform plan -detailed-exitcode pipeline. If drift is detected, automatically notify SREs or trigger an auto-apply to overwrite unapproved changes. [1]

Layer 4 — Staff: GitOps with Config Connector & Policy Controller

Staff architects implement GitOps: developers commit Kubernetes YAML manifests to Git. Config Sync syncs manifests to GKE, and Config Connector provisions the underlying GCP cloud infrastructure automatically. [1]

4 Hands-On Demo

Hands-On Demo: Configuring a Secure Terraform GCS Backend

Declare a remote Google Cloud Storage state backend with locking in your Terraform code.

# backend.tf
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }

  backend "gcs" {
    bucket  = "tf-state-brightloaf-prod-0123"
    prefix  = "terraform/state/production"
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

# main.tf
resource "google_compute_network" "vpc_network" {
  name                    = "custom-vpc-prod"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "subnet_app" {
  name          = "subnet-app-us-central1"
  ip_cidr_range = "10.10.1.0/24"
  region        = "us-central1"
  network       = google_compute_network.vpc_network.id
  private_ip_google_access = true
}
