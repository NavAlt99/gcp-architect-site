Infrastructure as Code: Terraform, GitOps & Config Connector

Declarative cloud engineering: Terraform modular architecture, remote state management in Cloud Storage with object locking, Cloud Foundation Toolkit blueprints, and Kubernetes-native Config Connector.

On this page

1 Real-World Explanation

The Situation: The Chaos of "ClickOps"

Provisioning cloud resources manually through the Google Cloud Console ("ClickOps") is an anti-pattern for enterprise workloads. It creates environments that cannot be reproduced, audited, or reliably recovered during a disaster.

Infrastructure as Code (IaC) treats cloud infrastructure with the exact same rigor as application code: written in declarative text files, version-controlled in Git, tested in CI/CD pipelines, and deployed automatically.

Core Terraform Concepts on Google Cloud
  • Declarative Syntax (HCL): You declare what the infrastructure should look like; Terraform calculates the dependency graph and steps needed to reach that state.
  • Remote State in Cloud Storage: Storing terraform.tfstate in an encrypted, versioned GCS bucket with automated locking prevents concurrent execution corruption.
  • Cloud Foundation Toolkit (CFT): Google's enterprise-grade, opinionated, production-ready Terraform modules that adhere to CIS security benchmarks.
  • Config Connector: A Kubernetes operator that allows you to manage Google Cloud resources (VPCs, Cloud SQL, Buckets) natively via Kubernetes Custom Resource Definitions (CRDs).

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Remote State Locking in GCS

Always configure a remote backend in Cloud Storage with Object Versioning enabled. Terraform uses GCS strongly-consistent metadata locking to prevent two engineers from applying changes simultaneously.

Layer 2 — Practitioner: Terraform Modules & Workspaces

Never write monolithic 5,000-line main.tf files. Break infrastructure into reusable modules (modules/vpc, modules/gke, modules/cloudsql). Use workspaces or folder-based environments (environments/dev, environments/prod).

Layer 3 — Architect: Drift Detection & Automated Reconciliation

Manual console changes create "configuration drift". Schedule a daily automated terraform plan -detailed-exitcode pipeline. If drift is detected, automatically notify SREs or trigger an auto-apply to overwrite unapproved changes.

Layer 4 — Staff: GitOps with Config Connector & Policy Controller

Staff architects implement GitOps: developers commit Kubernetes YAML manifests to Git. Config Sync syncs manifests to GKE, and Config Connector provisions the underlying GCP cloud infrastructure automatically.

Scope and planes

The resource model for Infrastructure as Code: Terraform, GitOps & Config Connector must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Hidden dependencies and day-2 operations

Review DNS, IAM, metadata access, quotas, Google APIs, upgrades, capacity changes, migration off the service, and deprecation risk. Keep ownership, escalation, and landing-zone guardrails explicit.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic:

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation.

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.

Hands-On Demo: Configuring a Secure Terraform GCS Backend

Declare a remote Google Cloud Storage state backend with locking in your Terraform code.

# backend.tf
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }

  backend "gcs" {
    bucket  = "tf-state-brightloaf-prod-0123"
    prefix  = "terraform/state/production"
  }
}

provider "google" {
  project = var.project_id
  region  = var.region
}

# main.tf
resource "google_compute_network" "vpc_network" {
  name                    = "custom-vpc-prod"
  auto_create_subnetworks = false
}

resource "google_compute_subnetwork" "subnet_app" {
  name          = "subnet-app-us-central1"
  ip_cidr_range = "10.10.1.0/24"
  region        = "us-central1"
  network       = google_compute_network.vpc_network.id
  private_ip_google_access = true
}
