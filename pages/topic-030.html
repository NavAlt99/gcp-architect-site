High Availability by Layer: Compute, Network, Storage & Database

Architecting multi-layer redundancy: Regional MIGs with autohealing, GKE multi-zone node pools, HA VPN dual tunnels, Spanner multi-region Paxos, and Cloud DNS failover routing.

1 Real-World Explanation

The Situation: Eliminating Single Points of Failure (SPOFs)

High availability (HA) cannot be achieved by focusing on a single layer. An application with a perfectly resilient Kubernetes cluster will still experience total downtime if it connects to a single-zone database, or if its DNS provider has an outage. [1] [2]

A true enterprise architect applies defense-in-depth redundancy across every layer of the technology stack: [1] [2]

The Four Layers of High Availability
  • Network Layer: Cloud DNS (100% SLA guarantee), Global External Application Load Balancers, Cloud HA VPN (two active tunnels in separate gateway interfaces for 99.99% SLA), redundant Cloud Routers with BGP. [1] [2]
  • Compute Layer: Regional Managed Instance Groups (MIGs) distributing VMs evenly across 3 zones with autohealing; GKE Regional Clusters with multi-zone node pools and Pod Disruption Budgets (PDBs). [1] [2]
  • Database Layer: Cloud SQL Regional HA (primary and standby in separate zones with synchronous block-level replication); Cloud Spanner (multi-region synchronous Paxos replication across 3+ regions with 99.999% SLA). [1] [2]
  • Storage & Messaging Layer: Dual-Region or Multi-Region Cloud Storage buckets with turbo replication; Cloud Pub/Sub with automatic global message replication across multiple zones. [1] [2]

Foundation references: VPC network overview · Google Cloud network connectivity overview

The Pain

High Availability by Layer: Compute, Network, Storage & Database becomes risky when teams treat **Compute:** regional MIGs across 3 zones, autohealing, over-provisioning for N+1, GKE regional clusters, multi-zone node pools, Pod Disruption Budgets, topology spread constraints as a checkbox instead of a boundary with an owner, evidence, and recovery path. [1] [2]

The Idea in One Paragraph

High Availability by Layer: Compute, Network, Storage & Database is a design decision anchored by **Compute:** regional MIGs across 3 zones, autohealing, over-provisioning for N+1, GKE regional clusters, multi-zone node pools, Pod Disruption Budgets, topology spread constraints. 2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Zonal vs Regional vs Multi-Regional Deployments

Zonal resources (single VM, single persistent disk) fail when the zone fails. Regional resources (Regional MIG, Cloud SQL HA) survive single zone outages. Multi-region resources (Spanner, Multi-Region GCS) survive entire regional disasters. [1] [2]

Layer 2 — Practitioner: Health Checks (Shallow vs Deep) & Autohealing

Configure separate Readiness Probes (is the app ready to take traffic?) and Liveness Probes (is the app deadlocked and in need of a reboot?). Never let a health check query an external database (deep probe); a database slowdown will cause the LB to kill all app instances simultaneously! [1] [2]

Layer 3 — Architect: GKE High Availability Primitives

Enforce topologySpreadConstraints to balance pods across failure zones; configure PodDisruptionBudgets (PDB) to ensure at least 80% of replicas remain available during node pool upgrades. [1] [2]

Layer 4 — Staff: Multi-Region Active-Active Data Synchronization

Staff architects navigate CAP theorem trade-offs: choosing between external consistency (Cloud Spanner Paxos) or eventual consistency (Bigtable multi-cluster replication with write conflicts resolved by last-write-wins). [1] [2]

4 Hands-On Demo

Hands-On Demo: Creating a Regional Managed Instance Group with Autohealing

Deploy a resilient regional compute cluster across 3 zones with automated health monitoring.

# 1. Create a health check for autohealing
gcloud compute health-checks create http hc-web-autohealing \
    --port=80 \
    --request-path="/healthz" \
    --check-interval=5s \
    --timeout=5s \
    --unhealthy-threshold=3 \
    --healthy-threshold=2

# 2. Create an instance template
gcloud compute instance-templates create template-web-v1 \
    --machine-type=e2-medium \
    --image-family=debian-12 \
    --image-project=debian-cloud \
    --tags=http-server \
    --metadata=startup-script='#!/bin/bash
      apt-get update && apt-get install -y nginx
      echo "Healthy" > /var/www/html/healthz'

# 3. Create a Regional MIG distributing instances across 3 zones
gcloud compute instance-groups managed create mig-web-regional \
    --template=template-web-v1 \
    --size=6 \
    --region=us-central1 \
    --health-check=hc-web-autohealing \
    --initial-delay=60s
