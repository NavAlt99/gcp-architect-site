Decision-Making Frameworks: ADRs & Trade-Off Matrices

Rigorous architectural evaluation: Build vs Buy vs Managed, weighted decision scorecards, Architecture Decision Records (ADRs), and Total Cost of Ownership (TCO) comparisons.

1 Real-World Explanation

The Situation: Why Architecture Decision Records Matter

In high-velocity engineering organizations, the question "Why did we build it this way?" is asked constantly. Without formal documentation, the context behind critical decisions is lost when senior engineers change teams or companies. [1] [2]

An Architecture Decision Record (ADR) is a lightweight text document that captures an important architectural decision made along with its context and consequences. Committing ADRs to source control alongside code creates an immutable audit trail of technical leadership. [1] [2]

Standard ADR Anatomy (Michael Nygard Template)
  1. Title: Short noun phrase with sequential ID (e.g., ADR-004: Use Cloud Pub/Sub for Asynchronous Order Ingestion). [1] [2]
  2. Status: Proposed, Accepted, Rejected, Deprecated, or Superseded. [1] [2]
  3. Context: The business context, forces at play, and constraints that motivated the decision. [1] [2]
  4. Decision: The change that we are committing to make. [1] [2]
  5. Consequences: The outcome of the decision—both positive benefits and negative trade-offs. [1] [2]
  6. Alternatives Considered: Other options explored and specific reasons why they were rejected. [1] [2]

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Build vs Buy vs Managed Service

Engineers love to build. Architects evaluate total lifecycle costs: building custom infrastructure requires 24/7 on-call rotations, security patching, and upgrades that detract from core business differentiation. [1] [2]

Layer 2 — Practitioner: Weighted Decision Matrices

Score options mathematically: assign weights to criteria (Operational Simplicity: 30%, Cost: 25%, Latency: 25%, Portability: 20%). Multiply scores (1-5) by weights to eliminate emotional bias. [1] [2]

Layer 3 — Architect: TCO & Reversibility (One-Way vs Two-Way Doors)

Jeff Bezos popularized "Type 1" (irreversible, one-way doors like database engine selection) vs "Type 2" (reversible, two-way doors like VM instance sizing). Spend deep analytical time on Type 1 decisions. [1] [2]

Layer 4 — Staff: Managing Technical Debt & Superseding ADRs

As business scale changes, architectures must evolve. When revisiting a decision, never edit the original ADR—create a new ADR that explicitly Supersedes ADR-004. [1] [2]

Technical references: Google Cloud Architecture Center · Architecture Framework decision principles

The scope of Decision-Making Frameworks: ADRs & Trade-Off Matrices is set by Build vs buy vs managed service. Separate the control-plane decision from the runtime path, and state which organization, project, region, zone, or resource owns the boundary. [1] [2]

4 Practice Exercise

Practice Exercise: Write an ADR

Write a complete ADR for Brightloaf Bakery deciding between Cloud SQL for PostgreSQL vs Cloud Spanner for their new regional loyalty rewards program (projected 200 writes/second, 1 TB total storage, budget constraint of $300/month).

Sample ADR: Loyalty Rewards Persistence

Title: ADR-012: Select Cloud SQL for PostgreSQL for Loyalty Service

Status: Accepted

Context: Loyalty service requires relational ACID transactions at 200 writes/sec with 1 TB storage. Monthly infrastructure budget is strictly capped at $300.

Decision: We will deploy Cloud SQL for PostgreSQL with Regional HA (db-custom-4-16) and automated cross-zone failover.

Consequences: Positive: Fits well within budget (~$180/mo); fully managed backups; standard Postgres SQL support. Negative: Limited to vertical scaling if traffic exceeds 10,000 writes/sec.

Alternatives Rejected: Cloud Spanner rejected because minimum cost (~$600+/month) exceeds the budget constraint, and extreme multi-region horizontal scaling is unnecessary for this workload.
