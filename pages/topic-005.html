1 Real-World Explanation

The Situation: The 12-Factor Foundation

At Brightloaf Bakery, the engineering team kept hard-coding database passwords into application files, writing logs directly to local VM disks, and building giant monolithic deployments where a CSS bug in the blog crashed the payment gateway. By adopting the 12-Factor App methodology and decoupling services into microservices, they gained independent deployment velocity, horizontal elasticity, and clean configuration management across environments.

Key 12-Factor Principles for Cloud Architects
  • Config in the Environment: Store database credentials and API endpoints in environment variables or Secret Manager, never in code.
  • Treat Logs as Event Streams: Write logs to stdout/stderr; let the cloud agent (Cloud Logging) aggregate and route them.
  • Stateless Processes: Execute apps as stateless processes; externalize state to Cloud SQL, Firestore, or Cloud Storage.
  • Disposability: Maximize robustness with fast startup and graceful shutdown handling SIGTERM signals.

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Monolith vs Microservices vs Serverless

Monoliths bundle all capabilities into one deployable unit. Microservices split services by domain boundaries (DDD). Serverless offloads scaling and infrastructure management entirely.

Layer 2 — Practitioner: REST, gRPC & API Contracts

Internal high-performance microservices communicate via binary gRPC over HTTP/2 with Protocol Buffers, while external web clients consume JSON RESTful APIs.

Layer 3 — Architect: Strangler Fig Migration Pattern

Never attempt a "big bang" rewrite. Route traffic through an API gateway and incrementally strangle monolithic features into serverless microservices one route at a time.

Layer 4 — Staff: DORA Metrics & Continuous Verification

Staff architects optimize the 4 DORA metrics: Deployment Frequency, Lead Time for Changes, Mean Time to Recovery (MTTR), and Change Failure Rate.

Scope and planes

The resource model for Software Architecture & Delivery Basics must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic:

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation.

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.
