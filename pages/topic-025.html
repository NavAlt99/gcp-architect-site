1 Real-World Explanation

The Situation: The 6 Rs of Cloud Migration

Organizations rarely move to Google Cloud by rewriting everything from scratch overnight. Attempting a "Big Bang" migration is the single highest-risk endeavor in IT. Successful cloud architects use the 6 Rs framework to determine the optimal strategy for each application:

The 6 Rs Migration Strategies
  • Rehost (Lift and Shift): Move VMs as-is to Compute Engine without code changes using Migrate to Virtual Machines (M2VM). Quickest path to exit a datacenter.
  • Replatform (Lift, Tinker, and Shift): Modernize the runtime without changing core code (e.g., move self-hosted MySQL to Cloud SQL, or package an app into a container for Cloud Run).
  • Refactor / Re-architect: Rewrite applications using cloud-native services (microservices on GKE, Pub/Sub, Spanner, Serverless). Highest business agility.
  • Repurchase (Drop and Shop): Replace bespoke software with commercial SaaS (e.g., moving self-hosted email to Google Workspace, or custom CRM to Salesforce).
  • Retire: Identify and decommission obsolete servers and applications that are no longer used (often 10-20% of an enterprise inventory).
  • Retain (Revisit): Keep workloads on-premise temporarily due to legacy dependencies, active hardware amortization, or regulatory sovereignty constraints.

The Pain

Without a deliberate Migration & Modernization: The 6 Rs & Wave Planning design, Brightloaf can see slow pages, failed orders, surprise spend, audit gaps, or a deployment that requires a weekend of manual work.

2 Technical Discussion & Architecture Diagrams

Layer 1 — Foundation: Discovery & Assessment (Migration Center)

Use Google Cloud Migration Center to inventory servers, track actual CPU/RAM utilization, identify oversized machines, and model Total Cost of Ownership (TCO).

Layer 2 — Practitioner: Data & Database Migration Mechanics

Use Database Migration Service (DMS) for minimal downtime replication of MySQL/PostgreSQL/Oracle to Cloud SQL/AlloyDB. Use Storage Transfer Service (STS) for large-scale object migration.

Layer 3 — Architect: Cutover Strategies & The Strangler Fig Pattern

Avoid big-bang cutovers. Use the Strangler Fig pattern: place an API Gateway in front of legacy systems and peel off individual routes to cloud microservices incrementally.

Layer 4 — Staff: Wave Planning & Rollback Engineering

Grouping workloads into migration waves (Wave 0: Landing Zone & Pilot; Wave 1: Non-critical internal apps; Wave 2: Core business services; Wave 3: Complex databases). Every wave requires a documented, tested rollback plan.

Scope and planes

The resource model for Migration & Modernization: The 6 Rs & Wave Planning must name its organization, folder, project, global, regional, zonal, or resource scope. Control-plane intent and data-plane traffic are different paths.

Practitioner defaults and troubleshooting

Set explicit project, region, identity, quotas, logging, and network dependencies. Treat undocumented internals as observed behaviour, may change.

Design-review questions

  1. What business requirement selects this service?
  2. What is its real scope?
  3. Which control-plane calls must succeed?
  4. What is the data-plane failure signal?
  5. Which quota or IP range saturates first?
  6. What is the blast radius of a bad policy?
  7. How are cost and usage attributed?
  8. How is rollback or migration tested?

What good looks like

  • Explicit scope and ownership
  • Least-privilege identity
  • Observable health and cost
  • Tested recovery and rollback
  • Documented alternative and exit path

Architecture diagrams in this curriculum are not decorative illustrations; they are precision engineering models designed to answer three distinct, non-overlapping architectural questions for every topic:

D1 — Scope & Boundary Map (Structural Lens)

Question Answered: Where do execution and security boundaries lie?
Maps components into their isolation perimeters (Client Edge vs Project VPC vs Managed Services). Establishes trust boundaries, network ingress choke-points, and data-plane vs control-plane separation.

D2 — Request & Control Flow (Runtime Ingress Lens)

Question Answered: How does production traffic traverse the architecture securely?
Traces an end-to-end operational journey—from ingress initiation and IAM perimeter validation across Andromeda SDN to backend state persistence and audit logging.

D3 — Failure Injection & Resilience (Chaos Lens)

Question Answered: How does the system degrade, alert, and auto-heal under catastrophic failure?
Models the exact mechanics of component saturation, network timeouts, and health check evictions under stress, revealing observability signals and automated failover pathways.
